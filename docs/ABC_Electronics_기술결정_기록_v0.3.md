## 2. 기술별 역할 설명

### 실행 흐름 관리와 대화 기억

LangGraph는 단계·분기·반복 등 실행 흐름을 구성하는 도구이며 이 서비스의 필수 조건은 아니다. Python 함수와 분기문으로도 조건 추출, 추가 질문, Tool 실행, 응답 검증을 구현할 수 있다. 이미 선택한 Session Repository가 대화 상태를 보관하므로, LangGraph를 제외해도 대화 기억 기능을 유지한다. LangGraph 사용 여부와 LLM이 Tool을 선택하는 권한은 별도 결정이다.

### JSON 스키마와 Tool Calling

JSON 스키마는 LLM의 응답을 정해진 양식으로 받는 방법이다. 예를 들어 의도=견적, 추천 순번=2, 수량=3으로 응답받은 뒤 서버가 필요한 Python Tool을 실행할 수 있다. 이 구성에서는 모델의 네이티브 Tool Calling을 사용하지 않아도 Product·RAG·Quote Tool은 실제로 동작한다.

네이티브 Tool Calling은 모델이 호출할 함수와 인자를 제안하도록 하는 방식이다. 실제 함수 실행·인자 검증·DB 접근 통제는 서버가 담당한다. JSON 스키마 방식과 Tool Calling은 함께 사용할 수도 있지만, 처음부터 두 방식을 모두 구현해야 하는 것은 아니다.

### DB 접근 코드와 DB 변경 기록

DB 접근 구현은 ‘상품 목록을 어떤 코드로 읽어올지’에 관한 결정이다. DB 변경 관리는 ‘새 세션 테이블이나 중복 방지 규칙을 팀원들의 DB에 어떻게 같은 순서로 적용할지’에 관한 별도 결정이다. 이번 기록 작성에서는 실제 DB나 프로젝트 코드를 변경하지 않았다.

## 3. 확정 정책을 기술 명세에 연결할 때의 기준

- SSE에는 진행 상태, 최종 성공 결과, 오류를 구분한다. 시작 전 입력·연결 오류는 적절한 HTTP 오류 코드로 반환한다. 이미 SSE 응답이 시작된 뒤에는 HTTP 상태를 뒤늦게 변경하지 않고 오류 이벤트를 보내 종료한다. 오류 코드와 재요청 안내를 이벤트에 담고 정상 완료 이벤트는 보내지 않는다.
- AI 설명 생성 실패 시 결과 대신 오류를 안내한다는 기존 선택은 유지한다. Tool 성공만으로 최종 성공 결과를 전송하지 않는다.
- 120초 제한은 진행 상태를 보냈다고 초기화하지 않는다. 읽기 조회·임베딩의 한 번 재시도도 같은 제한시간 안에서 수행한다. 같은 세션에서 대기 중인 요청의 시간 초과·취소와 중복 요청 연결 방식은 API 명세에서 일관되게 정의한다.
- 재전송 결과 재사용은 동일 요청의 중복 처리를 막는 기능이다. 새 request_id로 들어오는 견적 요청에서는 최신 DB 가격·재고를 다시 확인한다.
- 동일 request_id에 다른 입력이 들어오는 경우에는 이전 결과를 임의 반환하지 않고 충돌을 구분하도록 API 명세에 정의한다.
- DB 고유 제약 추가 전 기존 카드사 중복 데이터를 확인한다. 중복 방지와 적재 검증이 실제 적용됐다는 의미는 아니다.
- 현재 단계에서 코딩, DB 변경, 실제 모델 성능 측정 및 테스트 평가는 수행하지 않았다.

## 5. 기업 개발 관점의 선택과 사용 주체

### LangGraph 선정

LangGraph를 상담 실행 흐름 관리에 사용한다. 공식 문서는 기업 사용 사례와 코드로 정한 단계·LLM 기반 단계를 함께 구성하는 기능을 소개한다. 해당 기술의 시장 점유율이나 모든 기업의 표준이라는 주장은 하지 않는다. 본 프로젝트에서는 명확한 단계·분기와 테스트 가능한 실행 흐름을 구성하는 용도로 범위를 한정한다.

처리 흐름: 세션 복원 → LLM 의도·조건 JSON 추출 → Pydantic 검증 → 필수 정보 확인 → 정해진 경로로 Tool 실행 → 답변 생성·검증 → 상태 저장.

대화 기억은 기존 결정대로 Session Repository가 PostgreSQL에서 관리한다. LangGraph 체크포인트 저장소를 별도로 도입하지 않는다. 모델이 임의 SQL을 생성하거나 Tool을 자유롭게 반복 호출하도록 구성하지 않는다.

### DB 접근 모듈은 누가 사용하는가

| 주체 | 하는 일 |
|---|---|
| 프로젝트 개발자 | 공통 DB 접근 모듈과 조회문을 작성·테스트·수정한다. |
| 실행 중인 백엔드 서버 | 고객 요청마다 필요한 DB 조회와 세션 저장을 자동 실행한다. |
| ABC Electronics의 데이터 담당 직원 | 관리 화면에서 원본 PDF·Excel의 변경사항을 확인하고 승인 적재한다. 고객 상담을 위해 SQL을 직접 실행할 필요가 없다. |
| 고객 | 채팅으로 조건·선택을 전달하고 추천·재고·견적을 받는다. DB 접근 기술을 직접 사용하지 않는다. |

DB 접근 코드는 팀 프로젝트 개발에 포함되는 상시 서비스 구성요소다. 개발자가 한 번 작성한 뒤 서버가 상담 요청마다 반복 실행한다. 데이터가 변경되면 같은 코드가 최신 DB 값을 조회한다. DB 접근 모듈을 만든다고 주기적인 원본 파일 수집이나 판매 데이터 동기화까지 자동화되는 것은 아니다. 기존 원본 적재는 승인형이며 n8n 후처리는 핵심 기능 완성 후 별도 추가한다.

### DB 접근과 SQL 변경 파일의 실행 시점

- DB 접근 모듈(T05): 고객 요청마다 자동 실행한다. 상품·가격·재고 조회와 세션 읽기·쓰기를 담당한다.
- DB 구조 변경 파일(T13): 세션 테이블 추가나 고유 제약 추가처럼 구조가 바뀔 때 변경 버전별로 적용한다. 적용 이력을 기록해 같은 변경이 중복 적용되지 않게 한다.

### T05 확정 구성

SQLAlchemy Core가 조회문 구성·실행과 연결 수명 관리를 담당하고, psycopg 3이 PostgreSQL 연결 드라이버 역할을 한다. SQL Repository·Vector Repository·Session Repository를 공통 DB 접근 모듈에 두어 결과 표준화·예외·트랜잭션 처리를 모은다. DB 연결 풀은 SQLAlchemy Engine 계층에서 하나로 관리하며 별도 psycopg_pool을 중첩하지 않는다.

FastAPI의 동시 요청과 SSE를 고려해 상담 경로는 비동기 Engine·드라이버·모델 호출로 구성하는 것을 기술 명세의 기본안으로 한다. DB 트랜잭션은 실제 DB 처리 구간에 한정하고 LLM 응답 대기 중에는 연결을 붙들어 두지 않는다. pgvector 검색도 Vector Repository에서 파라미터가 있는 SQL 또는 타입 어댑터를 통해 수행한다.

현재 database/의 관리자 승인 적재 코드는 직접 psycopg를 사용하는 기존 구성으로 유지할 수 있다. 상담 backend/의 새 공통 모듈과 기존 ETL의 실행 책임을 구분한다. 이 선택은 고객과 직원의 화면 조작을 바꾸지 않는다. 실제 프로젝트 소스나 DB는 변경하지 않았다.
